# セラーリサーチ運用キット

`docs/dennou-sedori-tips.md` 7-2（セラーリサーチ）を実際に運用するための3点セット。
2026-09-22の議論を踏まえ、**作業分担を逆転させた設計**になっている。

## なぜAmazon側を人力、楽天側をAstraにするのか

セラーリサーチはAmazon起点の手法（セラー発見・出品リスト閲覧・出品者数確認は
すべてAmazon上の作業）だが、Astraはバッチ2・3ともAmazon側でアクセス拒否されている。
一方、楽天側（型番一致の確認・在庫・価格・転売禁止表記の確認）はAstraが2回とも
問題なく取得できている。

したがって、**Amazon側の調査は人間（Keepa等の正規ツール経由）、楽天側の確認はAstra**
という分担にする。これは12-5の「データ取得は正規ルート、AIには残りを任せる」の
考え方に沿っている。

## 全体の流れ（4段階）

```
①セラーリスト作成（人力・軽作業）
  ↓
②セラーの出品商品リストをKeepa等で確認（人力）
  ↓ ここで得た型番リストをAstraに渡す
③楽天側の価格・在庫・転売禁止表記をAstraが確認
  ↓
④analyze.pyで判定 → research-log/へ集計
```

### ①セラーリストを作る（`seller-watchlist.csv`）

- Amazon上で、評価数50〜400件・複数ブランドを扱うセラーを20〜30件探して記録する
- これは「今後複数回のバッチで使うタネ」であり、一度に全部処理しなくてよい
- **補助ツール（任意・未検証）**：普段のAmazon巡回のついでに条件（評価数レンジ）に
  合うセラーを検出し、追加確認バナーを出すブラウザ拡張機能を`browser-extension/`に
  用意した。追加の通信は行わず、開いているページのDOMを読むだけ。実機での動作は
  未確認のため、詳細と注意事項はそのディレクトリの`README.md`を参照
- **一度作ったら使い回す「定点観測リスト」**にする。`last_checked_date`を更新しながら、
  次回以降は「前回チェック以降に増えた新規出品」だけを見ればよい
  （新規出品の方が参入者が少なく、鮮度が高いため7-2の懸念にも合致する）

#### セラーが多くなってきたら：質による絞り込み運用（2段階）

セラーリストは多いほど候補の母数は増えるが、そのまま全セラーを毎回定点観測すると
チェックの手間が際限なく増えていく（リストが多いほど良いわけではない）。そこで
以下の2段階運用にする：

1. **広く集めて一度評価する**：新規セラーは一度②③④まで通し、`analyze.py`の判定結果
   （A/B/Cがどれだけ出たか、自分の仕入れ方針に合うか）をもとに、セラーごとの
   `quality_rating`（S/A/B/C）を`seller-watchlist.csv`に記録する。合わせて
   `last_evaluated_date`を更新する
2. **以降の定点観測はS/Aランクだけ**：`quality_rating`がS/Aのセラーだけを継続的に
   `last_checked_date`ベースで追いかける。B/Cランクのセラー（単一ブランド直営に近い、
   判定基準を満たす候補がほぼ出ない等）は`status`を`excluded`にして追わない
3. **評価は数ヶ月に一度やり直す**：`quality_rating`は一度付けたら固定ではない。
   セラーの出品傾向は変わりうるので、`last_evaluated_date`が古くなったセラーは
   （B/Cランクも含めて）再度評価し直し、リストを新鮮に保つ

この運用の鮮度チェックを自動化したのが`check_watchlist_freshness.py`：

```bash
python3 check_watchlist_freshness.py --watchlist seller-watchlist.csv

# 間隔を変えたい場合（デフォルトは評価90日・チェック14日）
python3 check_watchlist_freshness.py --watchlist seller-watchlist.csv \
    --evaluation-interval-days 90 --check-interval-days 14
```

このスクリプトは2種類のリストを出力する：

- **品質の再評価が必要なセラー**：`last_evaluated_date`が指定日数（デフォルト90日）
  以上前、または未評価のセラー全員（ランク問わず）
- **新着出品の確認が必要なセラー**：`quality_rating`がS/Aのセラーのうち、
  `last_checked_date`が指定日数（デフォルト14日）以上前のセラー
  （B/C評価のセラーは定点観測の対象外なのでここには出てこない）

### ②セラーの出品商品を確認する（`seller-products-template.csv`）

- ①のリストから**3〜5セラーずつ**選んで進める（一度に全部やらない）
- **Keepaのセラー検索機能を使う（2026-09-22確認済み）**：セラーIDをKeepaの出品者検索画面に
  貼り付けると、そのセラーの出品商品一覧を取得でき、必要な項目にチェックを入れて
  **CSVでエクスポートできる**（Excel形式も選択可）。これにより本キットの拡張機能を
  自作する必要がなくなる。**ただしKeepaの有料プラン（サブスクリプション）が前提の機能**。
  無料版は基本的な価格推移グラフの表示のみで、セラーリサーチ・エクスポート機能は使えない
- この段階で`amazon_price`・`seller_count`・`estimated_monthly_sales`（ランキング推移からの
  目安）まで埋める。**型番（product_name列に必ず含める）が次の段階で必須**

### ③楽天側をAstraに確認してもらう（`astra-prompt-rakuten-check.md`）

- ②で埋めた型番リストをそのままプロンプトに貼り付けてAstraに渡す
- Astraは楽天側の価格・在庫・転売禁止表記・型番一致のみを確認する
  （Amazon側は既に埋まっているので依頼しない＝Astraがブロックされる心配がない）

### ④統合して`analyze.py`で判定する

- `merge_seller_research.py`が②③の結果を商品名で自動的に突き合わせ、
  `../analyze.py`が読める1つのCSVに整形する（手作業での転記は不要）：

  ```bash
  python3 merge_seller_research.py \
      --amazon-side seller-products.csv \
      --rakuten-side rakuten-check-result.csv \
      --out merged.csv

  python3 ../analyze.py merged.csv
  ```

- 統合スクリプトは以下を**自動で除外**する（除外理由と件数はサマリーに表示される）：
  - 楽天側で在庫なし
  - ショップが転売目的の購入を拒否している
  - 型番が不一致
- 商品名の表記ゆれ（全角/半角スペース、連続スペース）はある程度自動で吸収するが、
  それでも突き合わせに失敗した行は警告として一覧表示されるので、手動で確認する
- 従来のバッチと違い、**最初からAmazon側・楽天側の両方が埋まった状態で判定できる**
  （バッチ2・3では毎回Amazon側が空欄でスキップされていたが、この分担ならその問題が起きない）

## ファイル一覧

| ファイル | 用途 |
|---|---|
| `seller-watchlist-template.csv` | ①セラーの定点観測リスト |
| `seller-products-template.csv` | ②Amazon側で確認した商品リスト（型番・価格・出品者数等） |
| `astra-prompt-rakuten-check.md` | ③楽天側確認をAstraに依頼するプロンプト |
| `merge_seller_research.py` | ④②③の結果を自動突合し、`analyze.py`用CSVに整形するスクリプト |
| `check_watchlist_freshness.py` | セラーリストの鮮度チェック（品質の再評価・新着出品確認が必要なセラーの一覧表示） |
| `browser-extension/` | ①セラー発見を支援するブラウザ拡張機能（任意・未検証、詳細はそのREADME参照） |

## 注意事項

- Keepaでの売れ行き分析は**代理指標**であり、正確な販売数ではない。出品者数が多い商品は
  「どのセラーの分が売れたか」は判別できない（7-2参照）
- ②③どちらの段階でも、有名ブランド・PSE・転売禁止表記などのリスクチェックは省略しない
  （「既に売られているから安全」とは限らない）
- 1セラーに候補が偏らないよう、`seller-products-template.csv`の`seller_id`列で
  後から集計し、複数セラーに分散しているか確認すること
